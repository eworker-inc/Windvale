# Windvale release envelope version 1

## Status

Release Envelope 1 is the implemented candidate for the first Windvale preview
release-signing and offline-verification boundary under
[Decision 0563](../Documents/Decisions/0563-First-Release-Envelope-And-Key-Policy.md).
Its focused owner is locally passing; official key generation, paired-host
qualification, final release-state selection, and `v0.1.0` publication remain
separate gates.

The format is deliberately smaller than The Update Framework. It is a bounded
offline release envelope with one pinned root and one delegated release key; it
does not claim TUF timestamp, snapshot, threshold, delegation, or network-update
protection.

## Cryptographic profile

Version 1 uses pure Ed25519 as specified by
[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) and admitted by
[FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final). This contract does
not claim that an arbitrary Node.js or host cryptographic provider is itself a
FIPS-validated module.

Public keys use canonical SubjectPublicKeyInfo DER. Private keys generated by
the repository ceremony tool use PKCS #8 PEM and never enter an envelope,
repository, CI secret, log, or release asset. A key identity is lowercase
SHA-256 over the exact public-key DER.

Signatures cover:

```text
ASCII "windvale-release-signature-v1" || NUL || ASCII kind || NUL || message
```

`kind` is exactly `root-policy` or `release-manifest`. This domain separation
prevents a valid signature over one metadata class from admitting the other.
Ed25519 signatures are exactly 64 bytes and are carried as canonical base64.

## Root policy

The first root policy is canonical strict UTF-8, uses LF, ends in one LF, and
contains exactly:

```text
windvale-release-root 1
policy-generation <positive-decimal>
algorithm ed25519
root-key <sha256> <spki-der-base64>
release-key <sha256> <spki-der-base64>
release-version-prefix <0.y.>
release-sequence-min <positive-decimal>
release-sequence-max <positive-decimal>
```

The root signature is a separate canonical file:

```text
windvale-signature 1
kind root-policy
algorithm ed25519
key <root-key-sha256>
message-sha256 <root-policy-sha256>
signature <ed25519-signature-base64>
```

An offline verifier receives the trusted root public key independently. It does
not trust the root key merely because it is embedded in the policy. The
embedded key must be byte-identical to the trust anchor and must verify the
policy signature.

Policy generation 1 authorizes exactly one replaceable release key, one `0.y.`
version prefix, and one inclusive sequence range. It has no civil-time or
network-freshness dependency. A caller can require a minimum release sequence
to reject an otherwise valid older envelope.

Root rotation, threshold roots, emergency revocation, and network freshness are
not silently approximated. A successor contract must require explicit old/new
root transition evidence and define recovery when the old root is unavailable.
Replacing the release key requires a new root-signed policy generation. Root
loss without an authenticated transition is a public trust reset, not an
ordinary update.

## Release manifest

The signed manifest is canonical strict UTF-8, uses LF, ends in one LF, and
contains:

```text
windvale-release-manifest 1
version <0.y.z>
channel preview
sequence <positive-decimal>
revision <40-lowercase-hex-git-object-id>
tree <40-lowercase-hex-git-object-id>
root-policy-sha256 <sha256>
release-key <sha256>
artifact-count <1..4096>
artifact <role> <target> <sha256> <bytes> <path>
```

Artifact records are ordered bytewise by role, target, and path. Roles,
targets, identities, byte lengths, and paths are ASCII-safe. Paths are ordinary
relative paths below `Artifacts/`; empty segments, `.`, `..`, absolute paths,
links, and special files are rejected. No role/target pair, exact path, or
ASCII-case-folded path may repeat. A role or target is at most 64 bytes; a path
is at most 1,024 bytes and 32 segments.

Every artifact is at most 268,435,456 bytes. One envelope admits at most
536,870,912 artifact bytes. Root inputs/policies and public/private key files
are at most 16,384 bytes, signatures are at most 4,096 bytes, and a release
input or manifest is at most 8,388,608 bytes. The complete release directory is
at most 8,192 file/directory entries. The creator reads and hashes each ordinary
source file once and publishes those already admitted bytes, preventing a
changed source from being copied after validation.

The `preview` profile requires exactly one artifact for each of these minimum
role/target pairs:

| Role | Target | Meaning |
| --- | --- | --- |
| `source` | `all` | Exact source archive for the selected revision/tree |
| `installer` | `windows-x64` | Qualified deterministic Windows installer |
| `installer` | `linux-x64` | Qualified deterministic Linux installer |
| `package` | `all` | Exact admitted WVDB Query Bundle 1 |
| `approval` | `all` | Capability approval and target launch records |
| `license` | `all` | Distributed license inventory |
| `provenance` | `all` | Bounded source/package/tool provenance |
| `recovery` | `stage0` | Immutable Stage 0 recovery reference and reconstruction identity |
| `qualification` | `windows-x64` | Exact selected-state Windows report |
| `qualification` | `linux-x64` | Exact selected-state Linux report |
| `verifier` | `all` | Offline verifier source selected by the manifest |

The installer payload manifests select their contained tools and licenses, so
an installer is the platform tool-distribution object rather than a second copy
of each executable in the release directory.

The release-manifest signature uses the same six-record signature format with
kind `release-manifest` and the delegated release-key identity.

## Offline verification

`Verify-Release-Envelope.mjs` is independently implemented from the creator. It
validates, in order:

1. the caller-provided Ed25519 root and its exact identity;
2. root-policy structure, embedded keys, sequence geometry, and signature;
3. release-manifest structure, policy selection, signature, canonical ordering,
   counts, paths, sizes, and required preview roles;
4. every artifact's ordinary-file type, byte length, and SHA-256; and
5. the bounded complete file and directory inventory, rejecting undeclared or
   missing entries.

The verifier performs no network access, extraction, installation, launch, or
capability grant. A valid signature proves that the delegated release signer
selected the exact bytes; it does not prove that the bytes are safe, grant them
runtime authority, or replace the named qualification reports.

The permanent owner generates ephemeral root and release keys outside the
repository, constructs the same envelope twice, proves exact determinism,
admits the valid directory, and rejects artifact, manifest-signature,
root-signature, trust-anchor, undeclared-file, rollback, unsafe-path,
incomplete-profile, release-key, and changed-source substitutions. No private
key enters a constructed envelope.

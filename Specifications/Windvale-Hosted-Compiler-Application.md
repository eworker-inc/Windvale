# Windvale hosted compiler application manifest

## Status and scope

`WVHA 1` is the implemented candidate manifest for packaging the exact ABI-22 Windvale compiler as paired Windows and Linux hosted applications. It binds the compiler's canonical six capabilities, exact ten required native services, platform adapter identities, service-table slots, service code, native image, and native entry. The manifest and service bundles are implemented and independently checked; public `windows-x64-console-v3` and `linux-x64-console-v3` targets and their startup/container layouts are not yet implemented.

The candidate allocates hosted container format 3 without changing the qualified version-1 or version-2 formats or bytes. It does not change WVB 1.6, WVO 1.0, native ABI 22, execution-context format 7, service-table format 5, the ordinary 4 MiB Windvale `bytes` limit, or the standard WVO/link admission profile.

## Exact compiler requirements

The manifest admits only the canonical exact compiler module. Its capability declarations remain in WVB order:

| Identity | Canonical capability | Signature identity |
| ---: | --- | ---: |
| 1 | `console.write_line` | 1: text to void |
| 2 | `diagnostic.write_line` | 1: text to void |
| 3 | `file.read_bytes` | 2: text to bytes |
| 4 | `file.write_bytes` | 3: text, bytes to void |
| 5 | `process.argument` | 4: u32 to text |
| 6 | `process.argument_count` | 5: void to u32 |

ABI 22 defines twelve possible service-table entries, but this compiler requires exactly ten. `text.quote` and `i32.format` are absent and their table slots must remain unbound.

## Service bundle

One service bundle starts with the unchanged independently verified native image. Required service leaves follow in service order under the canonical executable-publication placement plan. The first alignment gap is zero-filled, matching the retained publication contract; later executable alignment gaps are `0x90`. Every leaf is generated by its existing implementation and accepted by its separate instruction-level verifier before inclusion.

Adapter identities are serialized separately from semantic service identities:

| Identity | Adapter |
| ---: | --- |
| 1 / 2 | Windows `console.write_line` / Linux `console.write_line` |
| 3 | Process argument snapshot |
| 4 / 5 | Windows file input / Linux file input |
| 6 | Platform-neutral strict UTF-8 |
| 7 / 8 | Windows diagnostic output / Linux diagnostic output |
| 9 | Platform-neutral enum metadata |
| 10 | Platform-neutral text concatenation |
| 11 | Platform-neutral text quoting; defined but absent from this compiler |
| 12 | Platform-neutral i32 formatting; defined but absent from this compiler |
| 13 | Platform-neutral u32 formatting |
| 14 / 15 | Windows file output / Linux file output |

The exact Windows bundle is 17,143,635 bytes with SHA-256 `6d524aa9b96d0f624b0b449937ec6c0987a57e2c002af8276784c63a185efef6`. The exact Linux bundle is 17,143,351 bytes with SHA-256 `99da55911c81218ac74442a695d340ed440c74515b830bcc659bd4b7df7b2d4b`. Both begin with the same 17,130,441 native bytes and differ only in the four platform service leaves and resulting placement.

## `WVHA 1` binary layout

The manifest is exactly 1,024 bytes. All integer fields are unsigned 32-bit little-endian. Unknown identities or versions, changed counts, offsets, sizes, flags, digests, nonzero reserved fields, noncanonical capabilities, reordered services, target/bundle disagreement, or bundle-byte disagreement are invalid.

| Offset | Bytes | Field |
| ---: | ---: | --- |
| 0 | 4 | Magic `WVHA` (`0x41485657`) |
| 4 | 4 | Manifest version 1 |
| 8 | 4 | Manifest size 1,024 |
| 12 | 4 | Target: 1 Windows x64, 2 Linux x64 |
| 16 | 4 | Hosted container format 3 |
| 20 | 4 | Native ABI 22 |
| 24 | 4 | Execution-context format 7 |
| 28 | 4 | Service-table format 5 |
| 32 | 4 | Capability count 6 |
| 36 | 4 | Service count 10 |
| 40 | 4 | Capability-record offset 128 |
| 44 | 4 | Capability-record size 16 |
| 48 | 4 | Service-record offset 224 |
| 52 | 4 | Service-record size 64 |
| 56 | 4 | Bundle file offset, aligned to 16 |
| 60 | 4 | Complete bundle bytes |
| 64 | 4 | Native-image offset within bundle, zero |
| 68 | 4 | Native-image bytes, 17,130,441 |
| 72 | 4 | Native entry offset inside the native image |
| 76 | 4 | Record arena bytes, 2,097,152 |
| 80 | 4 | Dynamic text/byte arena bytes, 67,108,864 |

| 128 | 96 | Six capability records |

Each capability record contains numeric capability identity, its authority-bearing native service identity, signature identity, and contract version 1.

Each service record contains service identity at byte 0, capability identity or zero at byte 4, service-table byte offset at byte 8, adapter identity at byte 12, bundle-relative leaf offset at byte 16, leaf byte count at byte 20, flags at byte 24, reserved zero at byte 28, and the 32-byte leaf SHA-256 at byte 32. Flags are exactly 1 for an authority-bearing capability service and exactly 2 for an intrinsic service.

The current exact metadata SHA-256 values, using the candidate bundle file offset 4,096 and the canonical native entry, are `635c432f6af1349c54fee66a43aab7e89471ff5a42a04e6d1cdb29718ebc217d` for Windows and `179887b6dec8fd987301a07c290cda93e0833c6827d73d5e62f1ebcf05007d69` for Linux. An outer container may select a different aligned bundle offset only by producing and verifying the corresponding manifest bytes.

## Verification boundary and remaining work

The native fragment is verified before bundle construction. Every selected leaf is then verified independently, the complete ordered placement is reconstructed, and `WVHA 1` is parsed back against the actual bundle bytes. Focused malformed evidence covers count, capability, adapter, leaf digest, actual-bundle corruption, and target mismatch. Exact overall bundle and manifest identities are pinned for cross-host reproduction.

This contract does not yet initialize argument, output, file-input, or file-output tables; bind Windows imports or Linux syscalls; allocate their bounded private arenas; construct PE/ELF files; publish public targets; directly execute the packaged compiler; or prove .NET-free Stage 1 to Stage 2 reproduction. Those are successor container and startup gates. Stage 0 remains the builder, oracle, and recovery implementation.

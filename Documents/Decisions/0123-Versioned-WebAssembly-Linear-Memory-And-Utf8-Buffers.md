# Decision 0123: Versioned WebAssembly linear memory and UTF-8 buffers

- Date: 2026-08-02
- Status: Implemented with local Windows, Node.js, and Chromium evidence; cross-host and cross-browser qualification pending
- Extends: [Decision 0121](0121-WebAssembly-Calls-With-Structured-Control.md)
- Target: `wasm32-browser-v1-experimental`

## Context

Profiles 1 through 7 prove deterministic scalar lowering, checked arithmetic, exact metering, sequential structured control, bounded acyclic calls, and their composition. They exchange only an `i32` result through globals. That boundary cannot carry source text, bytecode, diagnostics, compiler output, or other variable-size values needed to remove .NET from the editable playground.

A browser host and a Windvale guest also need an explicit ownership contract. Depending on JavaScript strings, host object identity, a growable memory, or ad hoc pointer/length pairs would inherit host behavior and leave stale-memory, malformed-text, and resource-limit behavior unspecified.

## Decision

- Add experimental profile 8 for the exact compiler-produced identity forms `Main(Input: bytes) -> bytes` and `Main(Input: text) -> text`.
- Add execution ABI 3 with one import-free, fixed, non-growable 129-page WebAssembly memory. Reserve page zero; assign a host-owned 4 MiB input window at offset 65,536 and a disjoint guest-owned 4 MiB output window at offset 4,259,840.
- Export the run function, ABI global, memory, input and output offsets and capacities, mutable output length, immutable output kind, and mutable instruction count in a fixed order. `Windvale.run(i32 budget, i32 input_length)` returns a Windvale status.
- Represent opaque bytes as output kind `1` and strict UTF-8 text as output kind `2`. Validate text inside the generated module before any WVB instruction executes, including overlong, surrogate, out-of-range, truncated, and invalid-continuation rejection.
- Reset output length and instruction count before every invocation. Reject negative or over-capacity input length as `WVR3008`; preserve `WVR3011` metering; reject malformed text as `WVR3014`. Only status zero makes the output descriptor valid.
- Copy a successful value from the input window into the output window with WebAssembly `memory.copy`. The exact identity body charges four WVB instructions; budget three therefore fails with empty output after three charges.
- Extend the shared disposable worker to validate ABI 3, the exact export and memory shape, all published ranges, non-growth, input transport, output bounds, and host-side strict-UTF-8 agreement. Existing ABI 0 through 2 modules continue through their prior scalar paths.
- Advance the .NET-free static page to the 791-byte text artifact and make its input editable. The page encodes the edited value as UTF-8, transfers it to a fresh worker, and displays the round-trip text plus ABI, buffer, status, and instruction evidence.

## Consequences

The browser boundary can now move bounded bytes and Unicode text without .NET, host imports, ambient allocation, or a growable memory. Maximum-size copies are deterministic, malformed guest text fails in the guest, and the worker independently refuses invalid descriptors or layouts. Input and output ownership is explicit, so stale bytes outside a successful length are never observable result evidence.

This is a transport slice, not yet the compiler runtime. The selector accepts only identity functions and does not implement text operations, byte construction, scalar families beyond prior profiles, records, enums, dynamic allocation, collection, general calls over descriptors, a general WVB verifier, or source compilation in Wasm. The artifact is still produced by the Stage 0 toolchain and the normal editable playground still uses .NET.

## Local evidence

The bytes fixture compiles to 179-byte WVB SHA-256 `3d751ca734faed1832b4d33a9f0cfc605b695f3ae8156e3d431504798869c8d9` and deterministic 435-byte Wasm SHA-256 `b5f87bd47be7a0ce0bb6755de4ecea8bc311c9412ee28d6091092e7aa4c184f5`. The text fixture compiles to 178-byte WVB SHA-256 `c19463d24d65c1bc46dca48dcda8541491b53b7289483afe4508685f30e0fbda` and deterministic 791-byte Wasm SHA-256 `c3635b8df4ed9d471faad7e653e975662099c0a2336639586915ce50b768542d`.

The independent C# decoder reconstructs the exact input WVB function and emitted Wasm type, memory, exports, globals, wrapper, meter, UTF-8 validator, and copy operation. The reference interpreter confirms the same bytes and text identities. Node.js executes empty, ordinary, Unicode, arbitrary-byte, and exact-4-MiB inputs; rejects memory growth; produces `3011/0/3` at budget three; produces `3008/0/0` for invalid lengths; and tests curated malformed sequences plus 20,000 deterministic generated byte strings against `TextDecoder` in fatal mode.

`npm run verify:wasm-demo` independently reconstructs the embedded 791-byte artifact and verifies success, exhaustion, malformed UTF-8, exact layout, and memory non-growth without loading .NET. On 2026-08-02, a Chromium-based in-app browser executes both the default and a 62-byte multilingual edited value in fresh workers. It reports exact success `0/4`, exhaustion `3011/3`, identical output, zero .NET/Blazor requests, and no console warning or error. This is one browser-engine family; cross-host construction and cross-browser qualification remain pending.

## Rejected alternatives

A single shared in-place buffer was rejected because host and guest ownership would overlap and a successful descriptor could alias mutable input state.

A growable memory was rejected because buffer offsets and host views could change, and an unbounded guest growth policy would precede the allocator contract it is supposed to support.

Host-only UTF-8 validation was rejected because a guest entered by another conforming host must retain the same Windvale text semantics. The worker's decoder remains an independent cross-check, not the semantic implementation.

Encoding JavaScript UTF-16 strings directly into the ABI was rejected because WebAssembly memory is byte-addressed and Windvale text requires explicit strict UTF-8 semantics independent of a browser string representation.

## Reconsider when

- Representative compiler operations require scalar, text, bytes, record, enum, or bounded allocation support over this memory layout.
- More than one live input, output, or temporary value requires a versioned descriptor or allocator model.
- A Windvale-native WVB verifier or interpreter needs to consume canonical WVB directly from the input window.
- Cross-host or cross-browser evidence exposes an engine portability assumption in the current validator or bulk-memory copy.

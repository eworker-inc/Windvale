# Decision 0146: Expanded descriptor-bearing WebAssembly call graph

- Date: 2026-08-03
- Status: Implemented with local Windows and Node.js evidence; cross-host and cross-browser qualification pending
- Extends: [Decision 0144](0144-Modular-WebAssembly-Wvb-Canonical-Metadata-And-References.md)
- Target: `wasm32-browser-v1-experimental`

## Context

The canonical Windvale-written WVB semantic verifier occupies exactly all eight functions and all 65,536 aggregate code bytes admitted by WebAssembly profile 12. The remaining executable type/control-flow phase cannot be added without either removing a qualified semantic check or crossing both limits. Decision 0139 and Decision 0144 name that condition as a reconsideration trigger.

The next profile should add only the capacity needed to keep semantic phases separate. It must preserve the descriptor-bearing ABI, acyclic call proof, per-function bounds, deterministic output, and every earlier generated artifact.

## Decision

- Add experimental profile 13 over unchanged execution ABI 3. Profile-12 inputs retain their existing limits and generated bytes. A descriptor-bearing call graph uses profile 13 when it exceeds eight functions, 65,536 aggregate code bytes, or 200,000 aggregate decoded instructions.
- Accept two through sixteen `bytes -> bytes` functions, with `Main` still the only export and final canonical function. Every call must continue to target a lower canonical ordinal, bounding dynamic call depth to sixteen without recursion.
- Retain the profile-12 per-function ceilings: 2,047 nonparameter locals, 32,768 code bytes, 100,000 decoded instructions, and operand-stack depth four.
- Bound profile 13 to 131,072 aggregate code bytes, 400,000 aggregate decoded instructions, and 1,048,576 generated Wasm bytes. The 524,288-byte output ceiling remains active for profile-12-sized inputs.
- Raise the Stage 0 playground adapter's matching output and construction budgets to 1 MiB and 200,000,000 instructions. Decision 0149 subsequently raises only the construction ceiling to the measured 225,000,000 instructions needed by the complete executable verifier. The WebAssembly module remains import-free, uses fixed 129-page memory, and exposes the exact ABI-3 export set.
- Qualify the boundary with a derived nine-function semantic verifier. It inserts one real `bytes -> bytes` phase between `Main` and the existing nominal-type phase, crossing both old limits without copying or weakening the canonical verifier source. Reject a seventeen-function graph.
- Treat this as capacity for executable-flow verification, not the executable-flow proof itself. Typed operand stacks and local access under WVB's deterministic default-local semantics, call value flow, record-field receiver identity, joins, reachability, declared maximum-stack agreement, and capability authorization remain pending at this decision.

## Consequences

The complete verifier can now add up to seven separately owned phases and another 65,536 aggregate code bytes without changing the public browser ABI or routing descriptors through JavaScript. The larger bound remains finite and independently inspectable. Earlier profile artifacts, including the 440,093-byte profile-12 semantic Wasm module, retain their exact identities.

The selector's own WVB changes because the acceptance and output bounds are explicit Windvale code. Profile-12 construction performs a few additional limit checks, but its emitted Wasm is unchanged.

Profile 13 does not make arbitrary WVB safe to execute. The browser worker must still use the Stage 0 oracle until the executable-flow phase and authorization boundary are present and differentially qualified.

## Local evidence

The derived profile-13 verifier compiles to a 70,086-byte WVB module with nine functions and 65,567 aggregate code bytes. Its SHA-256 is:

```text
1b88f7cdbaf6d00fcde3ac6dfa09f38ff721e90edf283018378e5004a91340b4
```

The selector lowers it in 130,307,230 Windvale instructions to a deterministic 440,333-byte import-free Wasm module with SHA-256:

```text
8601f90946c0738ad6ce20c236e219f66e4ee4b2b143242a430c203918b1259a
```

The reference runtime accepts the hosted-capability fixture in exactly 113,464 instructions. Node.js accepts the generated module, instantiates it without imports, and agrees on the data/text, nominal-type, and hosted-capability inputs at 1,122,092, 912,958, and 113,464 instructions, including one-instruction-short exhaustion. The focused Seed WebAssembly test independently consumes all ten Wasm functions and rejects a seventeen-function WVB graph without output.

The updated standalone core WVB is SHA-256 `14be02c61ddfa0b8bcfab5804de8edf7cefa4dffe8c8b0d24762aee63b728222`. The composed hosted backend WVB is SHA-256 `fddf873732a2979c4a5fac25c02d10f91dcc71d7920b77293aed62354bb3e0f7`. Existing generated profile artifacts retain their exact bytes.

## Rejected alternatives

Removing canonical checks to remain under profile 12 was rejected because verifier capacity is not a reason to weaken the admission boundary.

Silently raising profile 12 was rejected because the eight-function and 65,536-byte limits are published evidence. Inputs that cross them have a distinct profile and larger explicit output bound.

Adding recursion or an unbounded function table was rejected because the verifier phases form an acyclic pipeline and decreasing ordinals retain the simplest static depth proof.

Duplicating the 1,642-line semantic source as a larger fixture was rejected because the capacity test only needs one derived phase and should remain coupled to the qualified source checks.

## Reconsider when

- The executable verifier needs more than sixteen functions or 131,072 aggregate code bytes.
- Measured compiler or interpreter work needs mixed signatures, nominal arguments, or bounded recursion.
- A mutable bounded verifier-state representation can replace allocation-free rescans and reduce code or browser latency without weakening validation.
- Profile 13 has matching Windows/Linux construction plus Chromium, Firefox, and WebKit execution evidence.
